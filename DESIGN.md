# Дизайн-документ проєкту

Проєкт — це багатомодульна Maven-збірка, що містить модуль застосунку та повторно використовувані модулі предметної області й інтеграцій.

## Модулі

- `game` — моделі персонажів, здібностей, спорядження та ігрових сесій. `GameEngine` — інтерфейс ігрової сесії. `AbilityProvider` — інтерфейс для створення здібностей.
- `api` — HTTP-клієнт Genshin API та перетворення віддаленого JSON на типізовані моделі. Для отримання даних використовується JDK `HttpClient` і джерело `genshin.jmp.blue` (`genshin.dev`). Бойові характеристики, яких API не надає, генеруються лише для ігрової моделі `Character`; DTO каталогу містить тільки дані з API.
- `text` — моделі документів і текстових елементів. `TextDocument` — інтерфейс документа. `TextDocumentFactory` — інтерфейс створення документів.
- `transport` — моделі транспортних засобів. `VehicleModel` — стабільний контракт транспортної моделі.
- `university` — моделі студентів, викладачів і людей. `PersonModel` — стабільний контракт моделі людини.
- `app` — адаптери командного рядка та точка збирання застосунку. Модуль залежить від `game` і `text`; модулі предметної області не залежать від `app`.

## Правила заміни реалізацій

1. Споживачі мають залежати від інтерфейсів із назвами, що закінчуються на `Engine`, `Model`, `Provider` або `Factory`.
2. Конкретні реалізації вибираються в конструкторах або в точці збирання застосунку.
3. Модулі предметної області не повинні імпортувати класи CLI або залежати один від одного, якщо цього не вимагає контракт модуля.
4. Наявні конкретні класи залишаються доступними як стандартні реалізації для сумісності.

## Поточне компонування

- `TextCli(BufferedReader)` за замовчуванням використовує `StructuredTextDocumentFactory` і також приймає власну реалізацію `TextDocumentFactory`.
- `GameCli(BufferedReader)` за замовчуванням використовує `DefaultAbilityProvider` і також приймає власну реалізацію `AbilityProvider`.
- `GameCli` за замовчуванням використовує `GenshinApiClient` і приймає `GenshinDataSource` для автономного тестування без мережі.

## Поведінкові шаблони проєктування

- `TextElementVisitor` викликає відповідну операцію залежно від типу структурованого елемента; `Text` використовує відвідувачі для відображення документа та створення змісту.
- `TextDocument` підтримує ітерацію в порядку елементів документа, не змушуючи клієнтів залежати від внутрішньої колекції.
- `Game` надсилає незмінні сповіщення `GameEvent` підписаним об'єктам `GameObserver` після змін ігрової сесії.
- `Game.saveState()` створює непрозорий об'єкт `GameMemento`; `restoreState()` відновлює стан ходів і змінні бойові характеристики гравців.
- `AbilityProvider` залишається точкою підміни стратегії створення здібностей.
- Реєстр команд застосунку продовжує передавати дії CLI відповідним реалізаціям `Command`.

## Команди Genshin

- `catalog characters` і `catalog refresh` звертаються до віддаленого API та виводять ідентифікатори доступних персонажів; `catalog weapons` виводить ідентифікатори зброї.
- `create char <api-id>` імпортує персонажа, генерує бойові характеристики відповідно до його рідкості та виводить структурований профіль.
- `create char` запускає діалог створення персонажа користувачем і запитує ім'я, бойові характеристики, опис (необов'язково) та URL графічного зображення.
- `ls char` виводить список збережених персонажів; `ls char --id <api-id-or-name>` показує профіль персонажа, зокрема посилання на графіку, якщо воно доступне.
- `create item <api-id>` імпортує зброю як спорядження.
- `add --char_id <api-id-or-name> --id <weapon-api-id>` додає імпортовану зброю персонажу й виводить оновлений профіль.

## Дизайн CLI: каталог персонажів

Для практичної роботи обрано тему **каталогу персонажів Genshin Impact**. Застосунок написаний на Java 21 і складається з Maven-модулів. Структура відповідних частин проєкту:

```text
app/src/main/java/com/myproject/
  Main.java                   точка входу CLI та вибір режиму
  CharacterCatalogWindow.java графічний каталог персонажів на Swing
  GameCli.java                цикл команд і сценарії роботи з каталогом
  CommandRegistry.java        розбір команд і передавання їх обробникам
  CharacterCatalogStore.java  збереження локального каталогу у форматі JSON
  CharacterTextRenderer.java  форматування профілю персонажа
api/src/main/java/com/myproject/api/
  GenshinDataSource.java      контракт джерела даних про персонажів і зброю
  GenshinApiClient.java       HTTP-реалізація джерела даних
  CharacterCatalogEntry.java типізована DTO-модель для каталогу та GUI
game/src/main/java/com/myproject/game/
  Character.java              бойові характеристики та стан персонажа
  CharacterProfile.java       метадані профілю та URL зображення
text/src/main/java/com/myproject/text/
  StructuredTextBuilder.java  засоби форматування тексту профілю

```

### Робота з консольним інтерфейсом

Запустити застосунок у режимі персонажів можна з аргументом `--chars` або вибравши режим `2` у початковому меню. Графічний каталог Swing запускається аргументом `--gui` або пунктом `3` меню; консольний режим тексту лишається типовим. `GameCli` показує доступні команди та зчитує їх по одній після кожного запрошення вводу. `CommandRegistry` розбирає аргументи в лапках, передає команди обробникам і виводить повідомлення про помилки, не завершуючи інтерактивний цикл. Команди `exit` і `quit` завершують роботу програми.

### Графічний інтерфейс: каталог персонажів

`CharacterCatalogWindow` побудований на Swing і показує персонажів у вертикальному прокручуваному списку композитних карток. Картка містить портрет, ім'я, рідкість, стихію, тип зброї, короткий опис, API ID та кількість здібностей. Панель керування включає текстовий пошук за ім'ям, ID, стихією або типом зброї та кнопку оновлення. Дані завантажуються фоновим `SwingWorker`, щоб мережеві запити API й кешування портретів не блокували вікно; помилки API показуються в інтерфейсі, а недоступні портрети позначаються на картці. Портрети використовують спільний `FilePortraitCache` у `%USERPROFILE%\\.genshin-cli\\portraits` (або `~/.genshin-cli/portraits`).

Вікно отримує список через `GenshinDataSource.listCharacterIds()`, завантажує типізований `CharacterCatalogEntry` для кожного ID та не залежить від випадкових бойових характеристик і станів ігрової моделі. Для запуску вікна використовується `Main --gui`; бібліотеки GUI не потребують додаткових залежностей, оскільки Swing входить до JDK 21.

| Команда | Дія |
| --- | --- |
| `catalog characters` | Запитує в Genshin API актуальний список ідентифікаторів персонажів. |
| `catalog refresh` | Оновлює та виводить віддалений список персонажів. |
| `catalog weapons` | Виводить доступні у віддаленому API ідентифікатори зброї. |
| `create char <api-id>` | Отримує персонажа з API, формує його профіль і бойові характеристики, виводить результат і зберігає його локально. |
| `create char` | Запитує ім'я, здоров'я, броню, атаку, опис (необов'язково) та обов'язковий URL графічного зображення; перевіряє характеристики через модель предметної області та зберігає профіль. |
| `ls char` | Виводить усіх персонажів локального каталогу, їхні бойові характеристики та URL графічних зображень. |
| `ls char --id <api-id-or-name>` | Показує характеристики персонажа, опис, здібності та посилання на графіку. |
| `create item`, `add`, `act`, `ls item`, `ls ability` | Наявні команди для спорядження та дій персонажів залишаються доступними. |

`CharacterTextRenderer` формує профіль за допомогою модуля структурованого тексту. URL графічного зображення показується як посилання. Якщо для персонажа, отриманого з API, URL не задано, використовується кінцева точка API з іконкою персонажа.

### Отримання та парсинг даних API

`GenshinApiClient` отримує перелік ідентифікаторів через `GET /characters`, а деталі потрібного персонажа — через `GET /characters/{id}?lang=en`. JSON розбирається Jackson у `JsonNode`, після чого `getCharacterCatalogEntry(id)` формує незмінний `CharacterCatalogEntry`. DTO містить ідентифікатор, ім'я, опис, рідкість, стихію, тип зброї, URL іконки та список здібностей із їхніми назвами, описами й типами. Дані бойових характеристик у цьому DTO не вигадуються.

Список здібностей об'єднується з API-масивів `skillTalents`, `passiveTalents` і `constellations`. Відсутні чи null текстові поля отримують безпечні порожні значення, некоректна рідкість — значення за замовчуванням API-адаптера, а список здібностей копіюється в незмінний список. Неуспішний HTTP-статус, переривання запиту або некоректний JSON передається як `IOException`, а не маскується під порожній профіль.

`CharacterCatalogWindow` запитує `GenshinDataSource.listCharacterIds()` для списку, а потім викликає `getCharacterCatalogEntry(id)` для кожного персонажа. Це дає UI окрему модель подання без залежності від бойових станів і випадкових характеристик `Character`. Для сумісності тестові чи альтернативні реалізації джерела даних можуть використовувати стандартний метод інтерфейсу, який формує DTO з уже наявної моделі персонажа.

Офіційний навчальний посібник Oracle зі Swing: [Creating a GUI With Swing](https://docs.oracle.com/javase/tutorial/uiswing/).

Якщо API недоступне, вікно переходить до офлайн-демонстрації з п'ятьма прикладами персонажів та локально намальованими умовними ілюстраціями. Рядок стану явно позначає демо-режим; ці картки не видаються за актуальну відповідь API чи офіційні портрети.

### Збереження даних і межі модулів

`CharacterCatalogStore` завантажує каталог JSON під час запуску режиму персонажів і зберігає його після створення чи імпорту персонажа, додавання спорядження або виконання дії. За замовчуванням файл розташований у `%USERPROFILE%\\.genshin-cli\\characters.json` у Windows або `~/.genshin-cli/characters.json` в Unix-подібних системах. У ньому зберігаються ідентифікатор для пошуку, ім'я, бойові характеристики, метадані профілю, здібності та URL графічного зображення. Помилкові або недоступні дані каталогу спричиняють повідомлення про помилку, а не непомітне створення порожнього каталогу. Шлях до файлу можна передати явно, щоб ізолювати дані в тестах.

`GameCli` відповідає за CLI та залежить від контрактів `GenshinDataSource` і `AbilityProvider`. `GenshinApiClient` є мережевим адаптером; під час тестування замість нього можна передати підроблене джерело даних. Моделі персонажа та його профілю належать модулю `game`, який не залежить від `app` або віддаленого API.

### Завантаження та кешування портретів

`GameCli` використовує `PortraitCache`; стандартна реалізація `FilePortraitCache` завантажує зображення після імпорту персонажа з API або створення персонажа з URL графіки. Кеш зберігається у `%USERPROFILE%\\.genshin-cli\\portraits` у Windows або `~/.genshin-cli/portraits` в Unix-подібних системах. Ім'я файлу є SHA-256 хешем URL, тому однакові URL відповідають тому самому локальному файлу, а дані URL не можуть впливати на шлях до файлу.

Перед мережевим запитом кеш перевіряє наявність непорожнього локального файлу; повторне використання URL не створює додаткового HTTP-запиту. Завантажуються лише абсолютні HTTP(S)-URL з відповіддю типу `image/*` розміром до 10 MiB. Дані спочатку записуються у тимчасовий файл і потім атомарно переміщуються до кешу, щоб неповне завантаження не залишало файл, який можна помилково використати повторно. Помилка завантаження явно виводиться в `stderr`, але не скасовує збереження персонажа: початковий URL залишається в його профілі, а `PortraitCache.cache(url)` повертає локальний шлях для майбутнього відображення з кешу. Директорію кешу можна задати явно для тестування.
